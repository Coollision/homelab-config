# GitOps structure: how a folder becomes a running app

[← Back to Home](../Home.md) · See also: [Bootstrap](bootstrap.md) · [Ansible](ansible.md)

This repo is a textbook "app of apps" ArgoCD layout, with one repo-specific twist worth
internalizing before touching anything: **the directory path *is* the deployment target.**

## The path → namespace convention

```
system/<namespace>/<app>/       ──▶  Application "<app>", namespace <namespace>, AppProject "system"
workload/<namespace>/<app>/     ──▶  Application "<app>", namespace <namespace>, AppProject "workloads"
tests/<namespace>/<app>/        ──▶  same, but from a separate git branch ("tests"), AppProject "tests"
```

This isn't a convention enforced by discipline — it's literally how the three
`ApplicationSet`s in `applications/` are written: a git *directories* generator matches
`system/*/*` (or `workload/*/*`), and `destination.namespace` is templated as
`{{index .path.segments 1}}` — the **first path segment becomes the namespace**, the
second becomes the Application name (`{{.path.basename}}`). A directory named
`disabled-<anything>` is explicitly excluded by the generator — that's the whole
mechanism behind every `disabled-*` folder you'll see scattered through `system/` and
`workload/`: present in Git for reference, but never deployed.

**Non-obvious consequence:** moving a chart's directory between namespaces (e.g.
`workload/services/radarr` → `workload/arr-stack/radarr`) is **not** a delete-and-recreate
from ArgoCD's point of view — since the Application name is just the folder's basename
(`radarr` either way), the ApplicationSet controller sees it as an in-place mutation of
the *same* Application's `source.path`/`destination.namespace`. This has real operational
consequences during a migration — see
[Known Issues → namespace migrations](../05-operations/known-issues.md#moving-a-workload-between-namespaces).

## ArgoCD manages itself {#argocd-manages-itself}

`argocd/` is ArgoCD's own Helm release, wrapping the upstream `argo-cd` chart plus this
repo's own values (Vault integration, ingress, health-check Lua overrides for Longhorn
CRs and Sablier-scaled apps, tuned reconcile concurrency — see
[Known Issues → repo-server OOM](../05-operations/known-issues.md#argocd-repo-server-oom)).
`argocd/templates/argo-app.yaml` is an Application whose `source.path` is `argocd` itself
— ArgoCD watches and reconciles its own Helm release. A second Application,
`argocd/templates/aplications-app.yaml`, points at the `applications/` directory below —
that's the actual root of the "app of apps" tree that fans out into every `system/*` and
`workload/*` chart.

## `applications/` — the fan-out layer

Three parallel pairs of (`AppProject`, `ApplicationSet`):

| Project | ApplicationSet | Source glob | Notes |
|---|---|---|---|
| `system` | `system-config` | `system/*/*` | `revisionHistoryLimit: 2` |
| `workloads` | `workloads` | `workload/*/*` | `revisionHistoryLimit: 3` |
| `tests` | `tests` | `tests/*/*` on branch `tests` | `revisionHistoryLimit: 1`, sandbox |

All three:
- use `goTemplate: true` + `missingkey=error` (a typo'd template variable fails loudly
  rather than silently rendering empty),
- render via the `argocd-lovely-plugin` Config Management Plugin — the same plugin that
  resolves every `<secret:kv/data/...>` placeholder against Vault at render time (see
  [Secrets — Vault](../01-platform/secrets-vault.md)),
- run `automated.selfHeal` + `automated.prune` — **a live `kubectl patch`/`kubectl edit`
  against a GitOps-managed resource gets reverted**, typically within seconds (see
  [Known Issues → Longhorn volumes are GitOps-managed](../05-operations/known-issues.md#longhorn-volumes-are-gitops-managed)),
- carry a machine-generated block of Sablier scale-to-zero `ignoreDifferences` entries
  (regenerated by `scripts/gen-scale-to-zero-ignores.sh`) between `BEGIN`/`END` marker
  comments — manually-added exceptions for apps that scale to zero *without* going
  through `shared-lib`'s `scaleToZero` flag live outside those markers on purpose, so the
  regen script doesn't delete them.

## `lib/` — shared Helm library charts

Almost no application in this repo hand-writes Kubernetes YAML. Instead, three tiny
`type: library` Helm charts turn a plain `values.yaml` into a full app:

- **`lib/shared-lib`** — the generic renderer used by the large majority of `system/` and
  `workload/` charts. From one `shared-lib.all` include, a chart's `values.yaml` can
  conditionally produce: a Deployment *or* StatefulSet, a Service, internal/external
  Ingress, a ServiceMonitor, Multus `NetworkAttachmentDefinition`s (VLAN legs), Longhorn
  or NFS storage, a Sablier scale-to-zero middleware, and an image pre-sync Job. Every
  consuming chart's `templates/app.yaml` is a one-liner:
  `{{ include "shared-lib.all" . }}`.
- **`lib/arr-lib`** — a thin wrapper around `shared-lib` used only by the arr-stack apps
  that need their SQLite config rewritten to point at Postgres (`arrXmlPostgres` flag) —
  see [Media Stack](../03-media-stack/overview.md).
- **`lib/longhorn-storage-lib`** — renders Longhorn `Volume` CRs + matching static
  `PersistentVolume`s from a `.Values.storage[]` list; used by the monitoring/logging
  stack, which pre-provisions its own storage this way instead of via `shared-lib`'s
  per-app storage block.

This "data, not code" convention is why most `workload/<app>/` and `system/<app>/`
directories you'll open contain only `Chart.yaml` + `values.yaml` + a one-line
`templates/app.yaml` — the actual Kubernetes shape lives once, in `lib/`, and every app
just fills in the blanks.

## Directory layout at a glance

```
argocd/          ArgoCD's own Helm release (self-managed, standalone Application)
applications/    AppProjects + ApplicationSets — the root of the fan-out tree
lib/             Shared Helm library charts (not deployed directly — consumed as deps)
system/          Platform/infrastructure — see 01-platform/
workload/        User-facing apps — see 02-smarthome/, 03-media-stack/, 04-apps/
tests/           Sandbox mirror of workload/system, synced from a separate git branch
docs/            Narrow runbooks for specific one-off procedures
scripts/         Operational scripts (scale-to-zero ignore-gen, sablier status, etc.)
ansible/         Node provisioning — see 00-setup/ansible.md
```
