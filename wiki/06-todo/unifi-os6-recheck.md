## 1. Does the mDNS limitation still hold?

- [ ] **Background:** UniFi's built-in mDNS proxy re-publishes records under its own identity. On the Matter/Thread
      VLAN that made the Thread border router see echoes of its own services and reject them as duplicates, so we run
      a verbatim L2 forwarder in the cluster instead (see [known issue](../05-operations/known-issues.md#mdns-reflector-must-not-re-publish)).
      UniFi's proxy stays limited to Cast/Android TV service types on the home and TV networks.
- [ ] **Check (read-only first):** do the OS 6 / Network 11 release notes or the mDNS settings page show a new
      mode, such as a pure reflect-only option or per-service/per-VLAN filtering that does not re-publish?
- [ ] **Only if a genuinely non-republishing mode exists:** test it on the `tests` branch stack or a throw-away
      network, never on the live Matter VLAN. Pass criteria: commissioning works, border-router logs show no
      `Duplicated` rejections, and Matter devices stay available in Home Assistant for a day.
- [ ] **Payoff if it holds up:** drop the in-cluster mDNS reflector (one less moving part). **If nothing changed,
      close this item and keep the reflector.**
- [ ] **Do not enable** the new Thread device monitoring feature: it needs mDNS and IPv6 on that network, which is
      exactly what must not be reflected.

### What UniFi's Matter/Thread feature actually is (researched 2026-11-10, third-party sources only)

- Network 11 can **monitor** Thread-based Matter devices (status, battery, firmware, signal; Thread devices appear in the
  topology view). It does **not** control devices or run automations: it is a second admin next to the existing controller.
- Each device must be added with **its own pairing code**, generated by the existing controller's "share" option. There is no
  single code or bulk enrolment that covers several devices (Matter multi-admin works per device).
- Requirements reported: gateway on UniFi OS 6.0.10 or newer, **mDNS and IPv6 on the network** that hosts the Thread border
  routers and devices, and at least one Thread border router (UniFi discovers existing ones).
- Direction reported by trade sites (not confirmed by Ubiquiti pages I could read): UniFi Connect Matter certification, an
  FCC-listed gateway product with a Thread border router, and a rumoured access point with a Thread radio. Reads as
  Thread **infrastructure plus monitoring**, not a smart-home hub. Open questions: whether a UniFi border router joins an
  existing Thread network or forms its own, and whether it re-publishes mDNS.
- **No API for it (checked 2026-11-10):** the official Network API spec v11.0.97 has the same 44 paths as v10.6.109 and no
  Matter, Thread or commissioning endpoint; the legacy and v2 APIs return 404 for any Matter path and the controller
  settings hold no Matter key. The only traces are an mDNS-proxy service category `MATTER_NETWORK` and a per-network
  `mdnsForwardingEnabled` flag. Enrolment is UI-only, one device and one code at a time.
- **First real test (one plug, 2026-11-10):** enrolled in the UI and working. UniFi's mDNS setting and the per-network
  mDNS flags were unchanged afterwards (Matter VLAN still off), the border router showed normal SRP registrations and no
  duplicate-record rejections, and matter-server logged no warnings. The `Duplicated` lines in the border router log are
  802.15.4 MAC-layer retransmission filtering, not the old mDNS problem. Unverified: how UniFi reached the plug without mDNS
  on that VLAN.
- Our situation: Home Assistant already shows the Thread role and channel per device, and the border router exposes its
  router table, so UniFi would mostly add a map. The risk side is the mDNS requirement on the Matter VLAN.

## 2. Is `mcast_to_unicast` still needed, and does the watchdog still work?

- [ ] **Background:** live TV on the bedroom decoder (behind a WiFi mesh hop) only works because the gateway's
      Linux bridge turns multicast into unicast per IGMP listener. UniFi resets that flag on every reprovision, so a
      small watchdog on the gateway re-applies it (see [IPTV](../01-platform/iptv.md#keeping-it-on-the-watchdog)).
- [ ] **Check 1, does the watchdog still run?** After the update the timer must be active and the Home Assistant
      heartbeat must be arriving. The update re-provisions devices, so one self-repair in the logbook is normal.
- [ ] **Check 2, did UniFi add a native option?** Look for a multicast-to-unicast or IPTV/multicast-enhancement
      setting for the TV network or the mesh radios in the new release. If it exists and is persistent, it can replace
      the watchdog (then run its `uninstall.sh`).
- [ ] **Check 3, does the flag survive a reprovision by itself?** Compare the watchdog's re-apply counter before
      and after the next natural reprovision. Do **not** disable the watchdog to test this: a stuttering TV is the
      failure mode.
- [ ] **Pass criteria for removal:** native setting found, bedroom decoder holds live TV for a full evening, mesh
      5 GHz airtime stays near the post-fix level (about 22%, not the old ~89%).
- [ ] **If nothing changed:** keep the watchdog and note the re-check date in the IPTV page.
